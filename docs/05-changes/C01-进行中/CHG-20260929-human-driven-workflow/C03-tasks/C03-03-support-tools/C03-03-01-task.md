# C03-03｜观测与语义工具兼容

> 用户已授权直接串行实施，由当前 Agent 在当前工作区执行；无需 Worker 或 worktree。本 Task 为宏观设计，实际结果与验证见 Delivery。GPU 能力退出已由用户明确确认；本 Task 不代替整体实际验证与最终人工验收。

## 目标

保留观测、诊断和可选语义工具，同时让它们理解人工流程：没有 Graph 是正常输入，串行不会被建议另起 Worker。

## 范围与分工

- 新流程文档无旧 index 映射、Graph 或 attempt 时仍可进行安全的只读关联和诊断。
- 历史 Graph、Task history、观测库继续可读；旧状态规则只用于历史分析，不控制当前阶段。
- 无法取得事件、时间或角色信息时如实标记未知/partial，不推造缺失 Worker、卡住或坏图等结论。
- System One / typesafe-laya 的模式和委派建议采用新角色语义，不再由 task_graph_ready 决定执行。
- 工具建议不代替用户阶段确认；继续保持显式启用、默认关闭以及既有秘密和本地记录保护。

不新增审批数据库、不改写历史 SQLite 记录、不从观测中自动重规划或派发。安装分发与完整消费验证由 C03-04 完成。

## 输入与依赖

消费 C03-01 的新模式与角色说明。不需等待 C03-02 的自动命令删除即可调整主体能力，但结果必须可在旧 workflow 完全退出后的整体环境中运行。

公共方案见 [整体设计与 Node.js 迁移范围](../../C02-design.md)，执行方式见 [任务计划](../C03-task-plan.md)。

## 总体实现方向

将新文档关联和旧工件解析视为两类只读输入；保留必要历史解析而不是复制旧执行状态机。语义建议基于实际模式、阶段与用户选择的执行方式；外部模型或 MCP 输出不获得写权限。

具体文件、函数、模块整理与编码步骤由执行者按真实调用链决定。任务内的小调整可自行完成，重要调整写入 Delivery；只有实质业务或公共边界变化才请用户确认。

## 验收与验证方向

- 无 Graph、无旧 frontmatter 的新 Change 能正常观测和打包诊断，缺少会话数据时如实报告。
- 有旧 Graph 的记录仍可读，历史数据未被清除、伪迁移或当作新流程授权。
- Quick 与串行建议保持当前 Agent；并行 Worker 建议遵循人工确认和任务实际依赖，Reviewer 仍仅按明确请求。
- Provider/工具传输、SQLite scope/权限、缓存或 fallback 等保留能力的相关安全回归不退化。
- 用观测、诊断和 System One 的定向测试验证新旧输入及建议边界。
