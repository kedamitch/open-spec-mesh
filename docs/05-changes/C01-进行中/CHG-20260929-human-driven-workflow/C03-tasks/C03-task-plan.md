## 已授权串行执行

这是同一工具包的流程与运行时重构，当前工作区已有未提交的 Node.js 迁移改动。串行可直接消费这些真实修改与前序结果，避免建立并行共享基线、安装包断耦和集成往返的额外成本，符合“当前 Agent 继续执行”的要求。

宏观依赖允许另一种选择：C03-01 完成后，C03-02 与 C03-03 可以并行，结果集成后再做 C03-04。但这只作为备选；本次用户已明确选择串行；并行写任务才启动 Worker 并用独立 worktree。需要先明确如何保全并向 worktree 提供未提交的必要输入，不能自动提交、stash 或重置当前工作区。

依赖来自真实产出，不把一次性的排程选择伪装成业务前置条件。若选择串行，同一实施阶段内可连续完成四项，不因每个 Task 结束自动要求一次新人工审批；实质边界变化仍请用户决定。

## 新增 Node.js 需求的影响

新增范围不能只合并成“安装包不带 Python”：还需覆盖剩余 Python 工具/测试、CI、Docker 示例，以及此前豁免的独立 GPU/Laya 服务。

C03-01/C03-02 需退出文档工具及自动生命周期的重复 Python 实现；C03-03 需核对客户端与真正 GPU 服务的区别；C03-04 需确保整个验证/分发环境没有 Python 前置。独立 GPU 服务以 C03-05 单列，用户现已明确确认退出该能力、保留外部 Node 客户端。按直接串行授权删除服务与专属依赖并验证保留能力，不重建冻结协议。

原流程宏观设计与串行方式已授权；完整 Node.js 目标按获准 GPU 能力退出落实。C03-05 需证明源码/依赖退出和 Node 客户端回归，原四项结果不代替最终人工验收。

## 执行中如何调整

- 各 Task 只约束目标、业务范围、必要公共约定和验收结果。执行者自行选择文件、函数、内部结构和具体步骤。
- 补充必要文件、局部修复、调整测试或实现方法可直接处理，重要调整写入 Delivery，不触发旧冻结或整图重规划。
- 目标、验收、安全或重要公共约定实质变化时，说明影响并等待用户确认；不按文件数或代码行数判断。
- 当前未提交修改是待保全基线，不应整体覆盖、回滚或作为本 Change 新增结果冒认。进入实施后按实际 diff 区分本轮增量。
- 不创建机器 Graph、摘要、attempt、派发身份或空 Delivery。实际完成每项时再记录相应 Delivery。
- 测试适配删除的自动能力，应说明有意退出的行为并覆盖新行为；不能通过删掉保留能力的回归、skip 或降低 AC 来取得全绿。

## 验证与阶段交付

每项完成相应能力的定向回归和必要静态检查；当前 Agent 收敛全部结果后运行适用的项目完整测试、构建、文档和打包验证。已验证且没有相关变化的结果可复用，避免重复运行；真实失败必须处理和记录。

全部保留能力迁移完成并通过适用验证后，提交实现结果供用户确认，才进入最终交付阶段。最终交付由当前 Agent 汇总证据、同步真实 Current Truth，并在用户最终验收后归档；不另起 Architect，不使用旧 receipt 门禁。

Current Truth 同步和项目全量验证是整体阶段职责，不另拆一个仅为了调用 Agent 的业务 Task，也不要求每个并行 Worker 运行全量。
